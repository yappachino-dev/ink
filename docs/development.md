# Development Guide

## Prerequisites

- Flutter SDK 3.47.5 (Dart 3.13.4) with Android tooling for the mobile target
- Go ≥ 1.26
- Buf CLI (protobuf toolchain; remote plugins declared in `buf.gen.yaml`)
- Docker + Docker Compose
- sqlc CLI (only when changing `services/core/db/queries/*.sql`)
- build_runner via the client's dev_dependencies

## Repository setup

1. Copy/create a root `.env` (loaded by Makefile, docker-compose, and the Go config):

```
DATABASE_URL=postgres://<user>:<pass>@localhost:5432/<db>?sslmode=disable
DB_USER=<user>
DB_PASSWORD=<pass>
DB_NAME=<db>
JWT_SECRET_KEY=<secret>
# development (default) logs verification codes; production refuses to
# start, because no CodeSender ships yet:
APP_ENV=development
```

## Backend workflow

```bash
make up          # docker compose up -d  (backend :8080/:50051 + postgres)
make build       # rebuild images and start
make down        # tear down
make restart     # down + up
make status      # compose ps
make logs        # follow logs

make migrate-up    # apply pending SQL migrations (goose, embedded FS)
make migrate-down  # roll back one migration
make migrate-status  # show migration status
make reset-db      # drop public schema and re-apply all migrations
make users|notes|projects|tokens|user-keys   # quick psql inspection queries
```

Regenerate Go/Dart protobuf code after editing `proto/**`:

```bash
buf generate          # uses buf.gen.yaml at repo root
```

Outputs:
- Go → `gen/go/pb` (module `github.com/yappachino-dev/ink/gen/go`)
- Dart → `client/lib/core/infrastructure/grpc/gen`

Buf also lints (`STANDARD`) and checks breaking changes (`FILE`) against `proto/`.

Regenerate sqlc code after editing queries:

```bash
cd services/core && sqlc generate
```

### Schema migrations (backend)

SQL migrations live in `services/core/db/migrations/` as goose-annotated files
(`00001_init.sql`, …), embedded into the binary via `db/migrations/embed.go`.
They are applied automatically on API-server boot (`database.Migrate` in
`internal/app/app.go`) — no manual step needed. For local/ops work the same
migrations are exposed through a CLI:

```bash
go run ./services/core/cmd/migrate [-url $DATABASE_URL] up|down|status|reset
# or via make (targets localhost:5432):
make migrate-up | migrate-down | migrate-status | reset-db
```

To change the schema: add a new `000NN_<name>.sql` with `-- +goose Up` and
`-- +goose Down` sections (never edit an applied migration), then regenerate
sqlc if queries are affected.

Troubleshooting: the postgres container creates `POSTGRES_DB` only when its
volume is empty. If you rename `DB_NAME` (or reuse a volume from an older
setup), boot fails with `database "..." does not exist` — create it manually:
`docker exec ink-db psql -U postgres -c 'CREATE DATABASE data OWNER postgres;'`
or wipe the volume (`docker compose down -v`) and start fresh.

Run the backend locally without Docker:

```bash
cd services/core && go run ./cmd/api
```

## Backend tests

```bash
cd services/core
go test ./...
```

Integration tests (`*_integration_test.go` in `auth`/`sync`/`vault`) boot a **throwaway Postgres via testcontainers-go** — Docker
must be running or they fail. Each test gets an isolated `postgres:18-alpine`
container with all embedded migrations applied through the same `database.Migrate`
path used on boot, then is torn down automatically.

The full suite was last run green with Docker available (`GOWORK=off go test
./...`): `auth`, `sync`, `vault`, `email`, and `ratelimit` all pass. Prefer
container-backed tests for anything touching SQL — unit tests with a fake
repository cannot catch a wrong query, a bad array binding, or a constraint
that does not exist.

### sqlc codegen

`internal/store/*.go` is generated by sqlc and must never be hand-edited. sqlc is
pinned as a Go tool in `services/core/go.mod`, so there is no global binary:

```bash
cd services/core
go tool sqlc generate
```

The pinned version is **v1.31.1**. Verify a clean tree stays clean after
regeneration before adding queries — a different version rewrites every file's
version stamp and produces a large spurious diff.

For array parameters, name the argument *and* keep the explicit cast:

```sql
WHERE id = ANY(@ids::uuid[]) AND user_id <> @user_id
```

Naming both parameters is required: with `@ids::uuid[]` and an unnamed second
argument sqlc fails to resolve the type, and with a bare `ANY($1)` it infers a
scalar `uuid` instead of a slice. The cast plus named parameters generate
`Ids []uuid.UUID` rather than the opaque `Column1 []uuid.UUID`.

## Client workflow

Client build-time environment variables:

| Variable | Purpose |
| --- | --- |
| `GRPC_HOST` / `GRPC_PORT` | gRPC endpoint |
| `ENV_NAME` | `development` allows plaintext only in non-release builds; all other values require TLS |
| `NETWORK_SECONDS_TIMEOUT` | RPC deadline, default 15 seconds |
| `GRPC_CERT_PIN` | Optional comma-separated SPKI pins in `sha256/<base64-sha256>` form |

Compute a standard SPKI pin from the server certificate, not from certificate DER bytes:

```bash
openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null 2>/dev/null \
  | openssl x509 -pubkey -noout \
  | openssl pkey -pubin -outform DER \
  | openssl dgst -sha256 -binary \
  | openssl base64 -A
```

Prefix the output with `sha256/` and pass it with
`--dart-define=GRPC_CERT_PIN=sha256/<value>`.

```bash
cd client
flutter pub get --enforce-lockfile
flutter run                # or flutter run -d <device>
flutter analyze            # very_good_analysis lint set
dart run tool/check_architecture.dart # import boundary guardrails
flutter test
```

### Android release signing

Release builds fail closed unless `client/android/key.properties` contains
`storeFile`, `storePassword`, `keyAlias`, and `keyPassword`. Copy
`client/android/key.properties.example` to `client/android/key.properties`,
then provide a locally managed release keystore; the properties file and
keystore extensions are ignored by Git. Paths in `key.properties` are resolved
from `client/android/app`.

```bash
cd client
flutter build appbundle --release
```

Never commit the keystore or populated `key.properties`. Debug builds continue
to work without release credentials.

Regenerate Riverpod/Freezed/Drift/retrofit/slang code after changing annotated sources:

```bash
cd client
dart run build_runner build --delete-conflicting-outputs
```

Never hand-edit `*.g.dart`, `*.freezed.dart`, `strings*.g.dart`, or files under
`lib/core/infrastructure/grpc/gen`. The production Inter font is bundled under
`assets/fonts/inter/`; golden tests disable Google Fonts runtime fetching so a
missing asset fails the test instead of falling back to Ahem.

### Schema migrations (client)

The Drift database (`lib/app/database/database.dart`) has a `schemaVersion` and a
real `onUpgrade` strategy. Schema snapshots live in `drift_schemas/*.json`,
generated test helpers in `test/migrations/schema*.dart`, and migration tests in
`test/migrations/migration_test.dart`. Workflow when changing the schema:

```bash
make schema-dump      # 1. snapshot CURRENT lib schema (before bumping the version)
# 2. bump schemaVersion in database.dart + write the onUpgrade step
make schema-generate  # 3. regenerate test/migration helpers
# 4. extend client/test/migrations/migration_test.dart for the new step
```

The generated `test/migrations/schema*.dart` files are excluded from analysis;
never edit them by hand.

Note: Argon2id runs with reduced memory (1 MiB × 1 iteration) in debug builds;
release builds use 64 MiB × 3.

## CI

GitHub Actions (`.github/workflows/ci.yml`) runs on every pull request (PRs are
the only path into `main`, and a squash-merge's content is identical to the
tested PR head — so no separate post-merge trigger; direct pushes to `main` are
not CI-checked):

| Job | Steps |
| --- | --- |
| Client · analyze & test | Runs for `client/**`, `proto/**`, or `buf*.yaml`: `flutter pub get --enforce-lockfile` → `flutter analyze` (errors, warnings **and infos are fatal** on the runner's Flutter) → `dart run tool/check_architecture.dart` → `flutter test` |
| Backend · build, vet & test | Runs for `services/**`, `gen/go/**`, `proto/**`, or `buf*.yaml`: runs `go build` / `go vet` / `go test` for `services/core` using its explicit local generated-module replacement |
| Protobuf · lint & breaking | Runs for `proto/**` or `buf*.yaml`: `buf lint` + `buf breaking` against `main` |
| CI gate | Always runs after path detection and fails if a required component job failed or was cancelled |

Notes:
- Concurrency group cancels superseded runs on the same ref to save minutes.
- The `changes` job uses `dorny/paths-filter`; unrelated component jobs are skipped, while the `CI gate` remains the required aggregate check.
- The committed `client/pubspec.lock` is enforced in CI; use `flutter pub get --enforce-lockfile` locally when validating dependency changes.
- The client must analyze with **zero issues of any severity** — `dart analyze` exits 0 with no output. On recent Flutter versions even info-level findings fail CI. Keep it that way; don't loosen the workflow with `--no-fatal-infos`.
- `dart run tool/check_architecture.dart` rejects presentation imports of feature
  data, core infrastructure/services, the app database, and other feature
  presentation modules. It also rejects feature data imports of the app database
  boundary. Extend the checker when introducing a new boundary rule.
- `dart fix --apply` clears most mechanical findings (const, directive order); long lines (>80 chars, `very_good_analysis` default) are fixed by hand.
- **Test determinism:** never "mutate" a random value with another constant (e.g. replacing a code's last digit with `'0'`) — it collides probabilistically. Derive mutations from the value itself (`(d+1)%10`). This class of bug only shows up on some CI runs.
- **CI pins Flutter to the local dev version** (`flutter-version: 3.47.5` in ci.yml). Do not switch back to a floating `channel: stable`: newer analyzers add lints (e.g. `unnecessary_unawaited` for `@awaitNotRequired` APIs) that don't exist locally, causing unfixable version-skew failures. Bump the pin deliberately, together with the local toolchain.

## Kubernetes

The `k8s/` tree is an experimental deployment path, not a current product
priority. It is explicitly deferred in `tech-debt.md` and should only resume if
Ink adopts Kubernetes.

```bash
cd k8s
kubectl apply -k .
```

- Requires `.env` and `.env.secrets` next to `kustomization.yaml`
  (secretGenerator/configMapGenerator).
- Deploys: postgres, core-service Deployment (gRPC liveness/readiness probes on
  :50051), ingress routing HTTP + gRPC.
- Local image expected as `core-service:local` with `imagePullPolicy: Never`.

## Conventions

The complete branch, atomic-commit, push, remote squash-merge, pull, and next-task
handoff workflow is documented in [workflow.md](workflow.md).

- **API changes** always start in `proto/`; regenerate both sides before writing code.
- **Client architecture**: feature-first Clean Architecture — domain interfaces +
  Freezed entities, data implementations (Drift/gRPC), Riverpod notifiers in presentation.
- **Errors**: sealed failure classes per feature, mapped to `CoreFailure`;
  operations return `Result<T, Failure>` instead of throwing.
- **New syncable entity**: implement the `Syncable` contract, add an engine/delegate
  pair under `features/<x>/data`, register it in `registeredSyncablesProvider`
  override at app startup.
- **Server-side secrets** never include user keys; only salts and wrapped keys pass through.
